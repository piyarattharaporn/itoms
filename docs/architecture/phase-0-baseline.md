# Phase 0 Baseline — Lotus IT Portal

Date: 2026-09-26

## Scope

This baseline covers the current Vite/React/TypeScript client, Firebase Authentication/Firestore boundary, Firestore Security Rules, and the Emulator-based test workflow. It does not approve production deployment or a Firebase production connection.

## Current strengths

- The application is split into feature services and React pages rather than putting all Firestore access in the application shell.
- Firestore Rules are deny-by-default and already enforce property-scoped access for the main operational collections.
- Authentication, profile, membership, and property boundaries are represented explicitly.
- Ticket creation and status transitions use a batch containing a domain event, and Ticket IDs are generated by Firestore.
- Operational Todo, PM, CCTV, and infrastructure incident writes have explicit validators and transaction/batch relationships.
- The project has an Emulator-based Rules test suite and a reproducible production build.

## Current risks

- Ticket assignment is reserved as an empty field but has no authorized assignment workflow yet. This must remain locked until the Assignment model is introduced.
- Some validators previously checked only the outer list shape; nested list elements and several text/date fields need stricter validation.
- Large list screens use bounded realtime listeners, but the read contract is not yet cursor-paginated.
- The User Directory service still subscribes to the full `users` and `memberships` collections. This is a scale and quota risk, even though regular-user collection listing is denied by Rules.
- The current Ticket event timeline is a domain history, not a complete append-only audit trail.
- There is no application-level usage/error monitoring contract yet.
- App Check is not initialized. It must be introduced as an opt-in production control and must not break Emulator development.

## Security boundaries

| Area | Requester | Client Executive | Support Engineer | Super Admin |
| --- | --- | --- | --- | --- |
| Own Ticket | Create/read own | Read property | Read/update status in property | Full scoped access |
| Asset | No management | Damaged/repair read where allowed | Manage property | Manage all active properties |
| PM | No access | Read property schedule | Manage property and runs | Manage all active properties |
| CCTV daily check | No access | Read enabled property | Manage enabled property | Manage all active properties |
| Infrastructure incident | No access | Read property | Manage property | Manage all active properties |
| Users/memberships/properties | No client writes | No client writes | No client writes | Read-only directory/property configuration as currently defined |

The source of authority is the authenticated UID plus the active profile and membership document. Client-supplied role, membership, `createdBy`, and property scope are not authority.

## Data invariants for this phase

- `propertyId`, `propertyCode`, creator fields, and creation timestamps are immutable after creation.
- A client-created Ticket starts in `Pending`, has an empty assignment, and must include its initial event in the same batch.
- Ticket status changes are Support/Super Admin operations and must include the matching immutable event in the same batch.
- PM runs must match the parent schedule checklist and advance the parent in the same write.
- CCTV daily checks use one document per property/date and require the authenticated checker.
- Unsupported collections remain denied until their own access model is reviewed.

## Deliberately deferred

Assignment/Reassignment, SLA timers and policies, cursor pagination, User Directory projection, Full Audit Log, scheduled workers, notifications, and usage dashboards are later phases. Phase 1 may reserve and lock fields needed by those designs, but must not invent a partial workflow.
