# คู่มือระบบ ITOMS ภาษาไทย

คู่มือนี้อธิบายวิธีใช้ IT Outsource Managed System ตั้งแต่การเข้าสู่ระบบ การจัดการ Task การติดตาม Incident การดูแล Asset และการอ่านรายงาน เหมาะสำหรับทีม IT Outsource ผู้บริหารบริษัท Outsource เจ้าของงาน และ Property Management

ระบบถูกออกแบบให้เป็นศูนย์กลางการติดตามงานและคุณภาพบริการ โดยใช้ข้อมูล Task เป็นหลัก แล้วเชื่อมโยงกับ SLA, Incident, Asset, RCA, Known Error และรายงานแบบ bounded/manual การอ่านข้อมูลจึงต้องคำนึงถึงขอบเขต Property และจำนวนรายการที่โหลดแล้วเสมอ

## 1. บทบาทและสิทธิ์

ระบบมี Global Role และ Property Role แยกกัน ผู้ใช้หนึ่งคนอาจมีบทบาทต่างกันในแต่ละ Property

| บทบาท            | เหมาะกับ                       | สิ่งที่ทำได้โดยสรุป                                                                                                              |
| ---------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Super Admin      | ผู้ดูแลระบบหรือผู้บริหารระบบ   | ดูและจัดการข้อมูลตามขอบเขตระบบ ดูทุก Property และจัดการการตั้งค่าที่ได้รับอนุญาต                                                 |
| Support Engineer | ทีม IT Outsource               | รับผิดชอบ Task ใน Property ที่ได้รับมอบหมาย อัปเดตสถานะ มอบหมายงาน แก้ไขข้อมูลปฏิบัติงาน จัดการ Asset/PM/CCTV/Incident ตามขอบเขต |
| Client Executive | ผู้บริหารหรือผู้แทนลูกค้า      | อ่านภาพรวม Task รายงาน Incident Asset PM CCTV และ RCA ตาม Property ที่ได้รับสิทธิ์                                               |
| Requester        | ผู้แจ้งงานหรือผู้ใช้งานหน้างาน | สร้างและติดตาม Task ของตนเองตามขอบเขตที่ระบบอนุญาต                                                                               |

สิทธิ์จริงถูกบังคับด้วย Firebase Authentication และ Firestore Rules ไม่ใช่ข้อมูลที่ผู้ใช้กรอกในหน้าจอ หากไม่เห็นเมนูใด ให้ตรวจ Role และ Membership กับ Super Admin

## 2. ส่วนประกอบของหน้าจอ

### Header

Header แสดงชื่อระบบ ชื่อผู้ใช้ ช่องค้นหา Task ภาษา Property และเมนูผู้ใช้

เมนูผู้ใช้แสดง:

- ชื่อและ Email
- Role
- Property ที่เข้าถึงได้
- User detail
- ออกจากระบบ

เมนูจะปิดเมื่อคลิกนอกพื้นที่หรือกด Escape ส่วนรูปผู้ใช้จะดึงจาก Google เมื่อเข้าสู่ระบบด้วย Google และมี `photoURL` ที่ใช้งานได้ หากไม่มีรูป ระบบจะแสดงตัวอักษรแรกของชื่อ

### Sidebar

เมนูถูกแบ่งเป็นกลุ่มเพื่อให้ผู้ใช้เลือกงานตามหน้าที่:

| กลุ่ม               | เมนู                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------- |
| ภาพรวม              | ภาพรวม                                                                                      |
| งานบริการ           | กระดานงาน, Create Task, ปฏิทินงาน, RCA & Service Review                                     |
| การปฏิบัติการ IT    | บันทึกเหตุขัดข้อง, กล้องวงจรปิด, บำรุงรักษาเชิงป้องกัน, อุปกรณ์และลิขสิทธิ์, อุปกรณ์เสียหาย |
| รายงานและการตรวจสอบ | รายงานผลงานบริการ, บันทึกกิจกรรม, บันทึก Audit Log                                          |
| การจัดการระบบ       | ตั้งค่า Property, ตั้งค่ารายการ, รายชื่อผู้แจ้งงาน, รายชื่อผู้ใช้                           |

เมนูจะแสดงตามสิทธิ์และการเปิดใช้งานของ Property เช่น CCTV จะแสดงเมื่อ Property เปิดใช้งานและผู้ใช้มีสิทธิ์อ่าน

## 3. Workflow หลักของ Task

### 3.1 สร้างงาน

เปิด `Create Task` แล้วกรอกข้อมูลให้ครบ โดยเฉพาะ Property หมวดปัญหา ประเภทย่อย และรายละเอียดปัญหา ข้อมูลเหล่านี้ใช้เป็นตัวกรองและรายงานในภายหลัง

คำแนะนำในการกรอก:

- หัวข้อหรือรายละเอียดควรบอกอาการ ผลกระทบ และจุดเกิดเหตุ
- ใช้พื้นที่หรือกลุ่มปัญหาให้ตรงกับ Guest, BOH หรือ Office
- เลือก Priority ตามผลกระทบจริง ไม่ใช้ Critical เป็นค่าเริ่มต้นทุกกรณี
- เลือก Asset เมื่อปัญหาเกี่ยวข้องกับอุปกรณ์ที่มีทะเบียน
- ระบุช่องทางการแจ้งให้ตรงกับแหล่งที่มา เช่น Email, LINE หรือ Personal Call

### 3.2 มอบหมายงาน

Support Engineer หรือ Super Admin เปิด Task Board แล้วใช้ช่อง `มอบหมายให้` เพื่อเลือกผู้รับผิดชอบ โดยระบบจะแสดง displayName เป็นหลัก ผู้ที่ไม่เกี่ยวข้องกับ Property จะไม่ควรปรากฏในรายการเลือก

หลังมอบหมาย ให้ตรวจว่า:

1. ชื่อผู้รับผิดชอบถูกต้อง
2. Property และพื้นที่ถูกต้อง
3. Priority สอดคล้องกับผลกระทบ
4. มีการเปลี่ยนสถานะเป็น In Progress เมื่อเริ่มดำเนินการ

### 3.3 เปลี่ยนสถานะ

ใช้สถานะเพื่อสื่อสารความคืบหน้า ไม่ควรใช้รายละเอียดข้อความแทนสถานะทั้งหมด

| สถานะ              | แนวทางใช้งาน                                        |
| ------------------ | --------------------------------------------------- |
| Pending            | งานเข้าระบบแล้ว รอเริ่มหรือรอผู้รับผิดชอบ           |
| In Progress        | กำลังวิเคราะห์ ตรวจสอบ หรือดำเนินการ                |
| Monitoring         | แก้ไขหลักแล้ว กำลังติดตามความเสถียร                 |
| Waiting for Vendor | ต้องรอ Vendor อะไหล่ ใบเสนอราคา หรือการเข้าหน้างาน  |
| Waiting for User   | ต้องรอข้อมูล สิทธิ์ การยืนยัน หรือเวลาจากผู้แจ้ง    |
| Completed          | ผลงานเสร็จ ผู้แจ้งหรือผู้รับผิดชอบตรวจสอบแล้ว       |
| Cancelled          | ไม่ต้องดำเนินการต่อหรือแจ้งซ้ำ โดยควรมีเหตุผลประกอบ |

### 3.4 แก้ไข Task หลังสร้าง

ระบบมี Controlled Edit สำหรับแก้ไขข้อมูลปฏิบัติงานที่คลาดเคลื่อน โดย Support Engineer และ Super Admin แก้ได้เฉพาะ:

- พื้นที่ทำงาน
- แผนก
- Asset ที่เชื่อมโยง
- รายละเอียดปัญหา
- Priority

ต้องระบุเหตุผลทุกครั้ง การแก้ไขจะถูกบันทึกเป็น Event/Audit ตามกระบวนการของระบบ ห้ามแก้ Property ผู้แจ้ง หมวดปัญหา ช่องทางการแจ้ง เวลา หรือข้อมูลหลักผ่านช่องทางนี้ หากเป็น Cancelled จะไม่อนุญาตให้แก้ไข

### 3.5 ปิดงาน

เมื่อเลือก Completed ระบบจะขอวิธีแก้ไขและบันทึกเวลา `completedAt` วิธีแก้ไขควรมีข้อมูลอย่างน้อย:

```text
สาเหตุ: สายสัญญาณกล้องหลวม
การแก้ไข: เสียบสายใหม่และตรวจสอบ PoE switch
ผลตรวจ: ภาพกลับมาใช้งานได้ต่อเนื่อง 15 นาที
การติดตาม: เฝ้าดูภาพจากกล้องในรอบตรวจถัดไป
```

เวลาแก้ไขเฉลี่ยในรายงานคำนวณจาก `completedAt - createdAt` และไม่นับงาน Completed ที่ไม่มี `completedAt`

## 4. Dashboard ภาพรวม

### 4.1 ขอบเขตข้อมูล

ก่อนอ่าน Dashboard ให้ดูชื่อ Property ขนาดใหญ่บนหน้าและ Property switcher ใน Header หากเลือก `ทุก Property` ตัวเลขจะสรุปตามรายการที่บัญชีมีสิทธิ์และระบบโหลดได้

ช่วงวันที่บน Dashboard ใช้กำหนดช่วงของข้อมูลที่ต้องการดู เช่น 7 วัน 15 วัน 1 เดือน 3 เดือน หรือกำหนดเอง ส่วนวันที่สรุปคือวันที่สร้าง snapshot ของหน้าจอ ไม่ใช่วันเวลาที่ทุกข้อมูลถูกเขียนพร้อมกัน

### 4.2 การ์ดสำคัญ

| ส่วน                    | ความหมาย                                            |
| ----------------------- | --------------------------------------------------- |
| เลยกำหนด                | งานที่เกินเวลาประเมิน SLA ในข้อมูลที่โหลด           |
| ใกล้ครบกำหนด            | งานที่เข้าใกล้เวลาประเมิน SLA                       |
| งาน Critical ที่ยังเปิด | งาน Priority Critical ที่ยังไม่ Completed/Cancelled |
| งานที่ยังเปิดอยู่       | งานที่ไม่ใช่ Completed หรือ Cancelled               |
| Response SLA            | สัดส่วนงานที่มีข้อมูลพอให้ประเมิน Response SLA      |
| งานที่ยังไม่เสร็จ       | รายการเปิดที่เรียง SLA ก่อน เพื่อใช้ติดตามหน้างาน   |
| บันทึกเหตุขัดข้อง       | Incident ที่ยังไม่กู้คืนหรือมีผลกระทบ Critical      |
| ติดตาม SLA              | ภาพรวม Response และ Resolution จากข้อมูลที่โหลด     |

### 4.3 งานที่ยังไม่เสร็จ

การ์ดนี้แสดงงานเปิดจากชุดข้อมูลที่โหลดแล้ว ไม่ได้แสดงเฉพาะงาน Critical การเรียงลำดับคือ:

1. เลยกำหนด
2. ใกล้ครบกำหนด
3. Critical ที่ยังอยู่ใน SLA
4. หยุดนับ SLA
5. อยู่ใน SLA

แต่ละแถวจะแสดง SLA Badge และ Workflow Status Badge แยกกัน เช่น `อยู่ใน SLA` + `กำลังดำเนินการ` เพื่อไม่ให้ผู้ใช้เข้าใจว่าสถานะงานกับสถานะ SLA เป็นเรื่องเดียวกัน

### 4.4 ความหมายของ SLA

SLA ใน Spark-only เป็นตัวชี้วัดเชิงปฏิบัติการแบบ Client-side ใช้เวลา 24x7 และใช้ข้อมูลที่มีใน Task ไม่มี Trusted Worker, Business Hours Calendar, Notification หรือการบังคับ SLA ตามสัญญา ดังนั้นควรใช้เพื่อช่วยจัดลำดับงาน ไม่ใช้แทนข้อตกลงสัญญา

## 5. Task Board และมุมมองข้อมูล

Task Board มีมุมมองตารางสำหรับข้อมูลจำนวนมาก และมุมมอง Kanban สำหรับดูงานตามสถานะ:

- ตารางเหมาะกับค้นหา เปรียบเทียบผู้รับผิดชอบ Priority และสถานะ
- Kanban เหมาะกับดู Workflow และงานที่ค้างในแต่ละสถานะ
- ใช้ตัวกรองสถานะร่วมกับช่องค้นหาเพื่อลดข้อมูลบนหน้าจอ
- บนจอเล็กให้ใช้ตัวเลือกสถานะแทนการพยายามดูทุกคอลัมน์พร้อมกัน

ข้อมูลผู้รับผิดชอบควรสื่อสารด้วย displayName ส่วน UID เป็นข้อมูลอ้างอิงภายในระบบและไม่ควรใช้เป็นชื่อเรียกในทีม

## 6. Incident Log

ใช้ `บันทึกเหตุขัดข้อง` สำหรับเหตุการณ์ที่กระทบการให้บริการหรือโครงสร้างพื้นฐาน เช่น ระบบล่ม กล้องหลายจุดใช้งานไม่ได้ หรืออุปกรณ์สำคัญขัดข้อง

ขั้นตอนแนะนำ:

1. เปิด Incident Log
2. เลือก Property และกรอกหัวข้อ เหตุการณ์ ผลกระทบ และเวลาเริ่ม
3. ระบุระดับ Impact เช่น Critical ตามผลกระทบจริง
4. ใช้สถานะ Open ระหว่างเหตุยังไม่กู้คืน
5. ใช้ Monitoring เมื่อแก้ไขแล้วแต่ยังเฝ้าดูผล
6. ใช้ Restored เมื่อกลับมาใช้งานและตรวจสอบแล้ว

Dashboard จะแยก Open, Monitoring และ Restored ให้เห็นว่างานใดต้องติดตามต่อ

## 7. RCA และ Known Error

### RCA

ใช้ `RCA & Service Review` สำหรับทบทวน Task ที่ Completed แล้ว บันทึกสาเหตุราก การแก้ไข และสิ่งที่ป้องกันไม่ให้เกิดซ้ำ RCA ควรใช้เมื่อเหตุการณ์มีผลกระทบ มีรูปแบบเกิดซ้ำ หรือมีบทเรียนที่ควรส่งต่อทีม

### Known Error

Known Error สร้างจาก RCA ที่ได้รับการ Approved แล้ว โดยข้อมูลหลักประกอบด้วย:

- อาการที่พบ
- Root Cause
- Workaround
- Permanent Fix
- ผู้รับผิดชอบ
- วันที่ต้องทบทวน
- สถานะ Draft, Published หรือ Retired

แหล่งอ้างอิงหลักยังคงเป็น RCA ส่วน Known Error เป็น snapshot สำหรับให้ทีมค้นหาและใช้งานซ้ำ ไม่ควรลบรายการเดิมเมื่อไม่ต้องการใช้ ให้เปลี่ยนเป็น Retired

## 8. Asset และอุปกรณ์เสียหาย

### Asset & Licence

ใช้ทะเบียน Asset เพื่อเก็บ Asset Tag ชื่ออุปกรณ์ ประเภท แผนก Location ผู้ขาย รุ่น Serial การครอบครอง และสถานะบริการ Asset ที่บันทึกแล้วสามารถเชื่อมกับ Task ได้

สถานะ Asset ที่ใช้หลัก:

- In Service: พร้อมใช้งาน
- Damaged: เสียหาย
- Under Repair: อยู่ระหว่างซ่อม
- Retired: เลิกใช้งาน

### อุปกรณ์เสียหาย

หน้า `อุปกรณ์เสียหาย` รวม Asset ที่เป็น Damaged, Under Repair และ Retired โดยมี Label แยกสถานะ เพื่อให้ทีมแยก “เสีย”, “กำลังซ่อม” และ “เลิกใช้งาน” ได้ชัดเจน

การเปลี่ยนสถานะควรทำในทะเบียน Asset แล้วใช้หน้าอุปกรณ์เสียหายเป็นหน้าติดตาม ไม่ควรสร้าง Asset ใหม่ซ้ำเพราะอุปกรณ์เดิมเสีย

## 9. CCTV และ Preventive Maintenance

### CCTV

หน้า CCTV ใช้ลงทะเบียน NVR และบันทึกผลตรวจรายวันแยกตาม Property/วันที่/NVR ข้อมูลที่โหลดและ Export เป็นข้อมูลแบบ bounded

ขั้นตอนตรวจ:

1. เลือก Property
2. เลือกวันที่หรือเดือนที่ต้องการตรวจ
3. ตรวจ NVR และจำนวนกล้อง Online/Offline
4. บันทึกหมายเหตุเมื่อพบความผิดปกติ
5. Export ข้อมูลที่โหลดแล้วเมื่อสิ้นรอบตรวจตามขั้นตอนของทีม

### Preventive Maintenance

ใช้กำหนดตาราง PM ตามรอบ เช่น Weekly, Monthly หรือ Quarterly และบันทึกผลการตรวจแต่ละรอบ การบันทึกผลควรระบุสิ่งที่ตรวจ ผลตรวจ และรายการที่ต้องติดตามต่อ

## 10. Service Performance และรายงาน

หน้า `รายงานผลงานบริการ` เหมาะสำหรับผู้บริหารและหัวหน้าทีม ใช้ดูปริมาณและคุณภาพตามช่วงเวลา โดยมีช่วง 7 วัน 30 วัน 90 วัน และ Custom range

แท็บหลัก:

- ผลงานทีม: งานที่มอบหมาย เสร็จ เปิดอยู่ ยังไม่มอบหมาย เกิน SLA และทำได้ตาม SLA แยกตามผู้รับผิดชอบ
- Property และปริมาณงาน: เปรียบเทียบจำนวนงานตาม Property หมวดปัญหา พื้นที่ และจุด/Asset
- คุณภาพและการทบทวน: ดู Resolution note, RCA และสัญญาณคุณภาพที่ระบบมีข้อมูลรองรับ

รายงานใช้ displayName เป็น Label หลักเมื่อมีข้อมูล Profile/Membership ที่ตรงกัน เวลาแก้ไขเฉลี่ยใช้ `completedAt - createdAt` และไม่นับงาน Completed ที่ไม่มี `completedAt`

### ขั้นตอนจัดทำรายงาน

1. เลือก Property หรือ `ทุก Property` ตามสิทธิ์
2. เลือกช่วงเวลารายงาน
3. กด `Load more` หากต้องการขยายชุดข้อมูล
4. ตรวจ `รายการที่โหลดแล้ว`
5. อ่านตัวเลขโดยอ้างอิงเฉพาะข้อมูลที่โหลด
6. กด Export มุมมองปัจจุบัน
7. บันทึกไฟล์พร้อมวันที่ ผู้จัดทำ Property และช่วงเวลา

## 11. Activities Log และ Audit Log

`บันทึกกิจกรรม` ใช้ดูประวัติการสร้าง เปลี่ยนสถานะ และมอบหมาย Task ตาม Property ที่มีสิทธิ์ ส่วน `บันทึก Audit Log` เป็นรายการเปลี่ยนแปลงที่มีประเภทการดำเนินการ รายการอ้างอิง รายละเอียด ผู้ดำเนินการ และเวลา

ใช้ชื่อผู้ดำเนินการแบบ displayName ในการสื่อสาร หากต้องการตรวจสอบระดับระบบให้ใช้รหัสอ้างอิงที่ระบบเก็บไว้ ไม่ควรนำ UID ไปใช้เป็นชื่อในรายงานทีม

## 12. การตั้งค่า

### ตั้งค่า Property

ใช้สำหรับข้อมูล Property และความสามารถเฉพาะ Property เช่น การเปิดใช้งาน CCTV ตามสิทธิ์ของผู้ดูแล

### ตั้งค่ารายการ

ใช้จัดการรายการที่ใช้ในแบบฟอร์ม เช่น หมวดปัญหา ประเภทย่อย ช่องทางแจ้ง และ Policy ของ SLA เมื่อรายการมีจำนวนมากควรตั้งชื่อให้สั้น ชัดเจน และเรียงตามอักษร

### รายชื่อผู้แจ้งงาน

ใช้จัดการ Request User ที่สามารถเลือกในแบบฟอร์ม Create Task โดยควรตรวจชื่อ Email แผนก และพื้นที่ทำงานให้ถูกต้องก่อนนำไปใช้

### รายชื่อผู้ใช้

ใช้ตรวจ Profile และ Membership สำหรับผู้ดูแลระบบ ห้ามใช้หน้าจอ Client เพื่อเปลี่ยน Role หรือให้สิทธิ์ Property แทนกระบวนการ Admin ที่ได้รับอนุญาต

## 13. การจัดการข้อมูลจำนวนมากบน Spark

ระบบใช้การอ่านข้อมูลแบบหน้า ๆ และโหลดเพิ่มตามความจำเป็น เพื่อควบคุม Firestore quota:

- หน้า Asset, PM, License และ Request User โหลดครั้งละประมาณ 25 รายการ
- รายงานและ Dashboard สรุปจากข้อมูลที่โหลดใน browser
- การค้นหาในบางหน้าค้นหาเฉพาะรายการที่โหลดแล้ว
- Export คือ Export มุมมองปัจจุบัน ไม่ใช่ Full database export
- CCTV มี Manual Export และ Retention ตามขั้นตอนของทีม

เมื่อข้อมูลเติบโตมากขึ้น ให้ใช้ Property filter, ช่วงเวลา, Search และ Load more อย่างมีแผน หลีกเลี่ยงการเปิดหลายหน้าที่อ่านข้อมูลจำนวนมากพร้อมกัน

## 14. แนวทางปฏิบัติที่แนะนำ

### ควรทำ

- ใช้ชื่อ Property และพื้นที่ตามมาตรฐานเดียวกัน
- ใช้ displayName ในการมอบหมายและสื่อสาร
- ปิดงานด้วยวิธีแก้ไขที่ตรวจสอบย้อนกลับได้
- ใช้ RCA กับปัญหาที่มีผลกระทบหรือเกิดซ้ำ
- เปลี่ยน Known Error เป็น Retired แทนการลบ
- ตรวจขอบเขตข้อมูลก่อนส่งรายงาน
- เก็บไฟล์ Export ในพื้นที่ที่ได้รับอนุญาตและกำหนดวันหมดอายุ

### ไม่ควรทำ

- ไม่ใช้ `ทุก Property` เพื่อสรุปแทนทุกข้อมูลโดยไม่ตรวจรายการที่โหลด
- ไม่สร้าง Task ซ้ำเพราะต้องการเปลี่ยน Property หรือพื้นที่ ให้ใช้ Controlled Edit เมื่ออยู่ในขอบเขตที่แก้ได้
- ไม่ลบ Task, Asset, Event หรือ Known Error เพื่อแก้ข้อมูลผิด
- ไม่ใช้ SLA Badge เป็นหลักฐานว่าเป็นการผิดสัญญา
- ไม่ใส่ Password, Service Account Key หรือข้อมูลลับลงในรายละเอียด Task หรือไฟล์ Export
- ไม่เปลี่ยน Role หรือ Membership จาก client code

## 15. วิธีรับมือเมื่อพบปัญหา

| อาการ                             | ตรวจสอบเบื้องต้น                                        |
| --------------------------------- | ------------------------------------------------------- |
| ไม่เห็น Property                  | ตรวจ Membership และสถานะ Active กับ Super Admin         |
| เมนูไม่แสดง                       | ตรวจ Role, Property scope และ Feature ที่เปิดใช้        |
| บันทึกไม่ได้                      | ตรวจสิทธิ์ Property ฟิลด์บังคับ และข้อความแจ้งเตือน     |
| รายงานตัวเลขไม่ตรงที่คาด          | ตรวจช่วงเวลา จำนวนรายการที่โหลด และกด Load more         |
| ชื่อผู้รับผิดชอบเป็นข้อมูลอ้างอิง | ตรวจ Profile/Membership displayName กับผู้ดูแล          |
| Google Sign-In ไม่ได้             | ตรวจ Provider และ Authorized Domain ใน Firebase Console |
| ข้อมูลเก่าหลัง Deploy             | Refresh หน้าและตรวจเวลา Last updated/Release            |

หากต้องส่งเรื่องให้ผู้ดูแล ให้แนบ Property, รหัส Task/Asset/Incident, เวลาที่เกิดปัญหา, หน้าที่เปิดอยู่ และข้อความ Error โดยไม่แนบ Credential

## 16. สรุปการใช้งานตามบทบาท

| บทบาท            | งานประจำวัน                                            | งานทบทวนรายสัปดาห์/รายเดือน                |
| ---------------- | ------------------------------------------------------ | ------------------------------------------ |
| Requester        | สร้าง Task ให้ข้อมูลครบ ติดตามและยืนยันผล              | ตรวจงานของตนเองที่ยังเปิด                  |

## 17. ข้อจำกัดสำคัญของรุ่นปัจจุบัน

ระบบรุ่นนี้ตั้งใจใช้งานบน Firebase Spark และ static Firebase Hosting จึงยังไม่มี:

- Scheduled notification หรือ escalation อัตโนมัติ
- SLA Worker ที่เป็น server-authoritative
- Full-text search ข้ามข้อมูลทั้งหมด
- Full database export หรือ managed backup จากหน้าเว็บ
- File upload และระบบแนบเอกสาร
- การกำหนด Role/Membership จากหน้า Client
- Audit ที่รับรองการแก้ไขแบบ tamper-proof

หากกระบวนการใดต้องใช้ความสามารถเหล่านี้ ให้บันทึกเป็นข้อเสนอ Phase ถัดไป ไม่ควรแก้ด้วยการเพิ่มสิทธิ์กว้างหรือใช้การ Export แบบ manual แทนโดยไม่ระบุข้อจำกัด
